# AGENTS.md — ZIYIT STUDIO 网页 UI 设计协作规范

> 本文档是 ZIYIT STUDIO 所有网页 UI 相关开发工作的**总纲**，与 `design/DESIGN.md`（视觉与交互标准）配套使用。
> 适用范围：全站所有页面，**除 `backrooms/` 目录以外**（该目录保持其原有独立风格，不适用本规范）。

---

## 1. 项目概述

- **品牌**：ZIYIT STUDIO（科技 · 创造 · 无限可能）
- **形态**：多页面静态站点（部署于 GitHub Pages），后端 API 独立部署
- **核心业务模块**：首页、用户中心、下载中心（Release Control）、人机验证、音乐分享、搜索、翻译工具、管理后台、更多工具（move）、ModWiki 等
- **目标**：全站 UI 统一、风格一致、体验连贯、开发高效

## 2. UI 设计核心原则与价值观

所有页面设计与实现必须遵循以下原则，按优先级从高到低：

### 2.1 一致性（Consistency）
- 同一功能、同一含义的元素，在任何页面必须使用**完全相同**的样式与行为。
- 色彩、字号、间距、圆角、阴影必须取自 `DESIGN.md` 定义的 token，禁止各自发明数值。
- 组件（按钮、表单、卡片、导航、模态框）优先复用已有统一样式，禁止重复造轮子。

### 2.2 简洁（Simplicity）
- 一屏之内聚焦核心任务，去除无关装饰。
- 信息层级清晰：一页只有一个视觉焦点（Hero / 主操作）。
- 能少一个字就不多一个字；能一个操作完成就不分两步。

### 2.3 用户导向（User-Centered）
- 每个操作必须有即时、明确的反馈（点击反馈、加载态、成功/失败提示）。
- 让用户可随时返回、可撤销（危险操作必须二次确认）。
- 以普通用户的理解能力为准，不依赖黑话与缩写。

### 2.4 品牌统一（Brand Unity）
- 主色、强调色严格取自品牌色板，构建"一眼 ZIYIT"的识别度。
- 所有页面共享同一套设计语言，但允许各功能模块在**组件层**做差异化表达（如管理后台更紧凑、内容页更宽松），**token 层不允许差异**。

### 2.5 可访问性（Accessibility）
- 正文与背景对比度 ≥ 4.5:1；大字号（≥24px）≥ 3:1。
- 可点击元素最小触控区域 ≥ 44×44px（移动端）。
- 表单控件需有 `label`；图片需有 `alt`；操作按钮需有可读文本。

## 3. 设计团队协作规范

### 3.1 角色与职责
| 角色 | 职责 |
|---|---|
| 设计师 | 维护 DESIGN.md、评审视觉产出、定义组件与交互 |
| 前端开发者 | 按 DESIGN.md 实现页面、复用统一组件、保证行为一致 |
| 审核人 | 在合并前按"评审清单"把关一致性与可用性 |

### 3.2 协作流程
1. 需求 → 先对照 DESIGN.md 判断是否符合既有模式；新交互需补充到 DESIGN.md 后再实现。
2. 实现 → 优先复用已有组件与 token，**禁止硬编码新色值/新间距**。
3. 自查 → 开发者按 §5 评审清单逐项自查。
4. 提交 → 变更记录写入 `design/CHANGELOG.md`。
5. 审核 → 审核人复查，通过后方可部署。

### 3.3 沟通机制
- 代码与文档注释统一使用**简体中文**。
- 类名采用小写字母 + 连字符（如 `.user-card`、`.btn-primary`），禁止中文类名。
- 涉及 UI 的改动在提交说明中注明 `[UI]` 前缀。

## 4. 设计评审流程

### 4.1 评审节点
- **设计阶段**：新页面 / 新组件草图确定后评审一次。
- **实现阶段**：页面完成后、部署前评审一次（对照 DESIGN.md）。

### 4.2 评审清单（Checklist）
- [ ] 色彩全部来自品牌色板，无游离色值
- [ ] 字体层级符合 DESIGN.md（字号/字重/行高）
- [ ] 间距符合 4px 基准刻度
- [ ] 按钮/表单/卡片等组件形态统一
- [ ] 交互有反馈（悬停/点击/加载/成功/失败）
- [ ] 危险操作有二次确认
- [ ] 移动端、平板、桌面三档均正常显示
- [ ] 背景为纯色或渐变，**无背景图片**
- [ ] 未涉及 `backrooms/` 目录内容

### 4.3 反馈方式
- 评审意见以"问题 + 依据（原则/规范条款） + 建议"三要素给出，便于执行。

## 5. 设计决策框架与冲突解决

### 5.1 决策依据层级
1. **设计原则**（本文档 §2）
2. **视觉/交互标准**（`DESIGN.md`）
3. **既有实现惯例**（已上线页面的一致做法）
4. **个人偏好**（仅在前三者空白时参考）

### 5.2 冲突解决机制
- 两个方案冲突时：先回到**设计原则**判断谁更符合；原则无法裁决时以 DESIGN.md 为准；仍存疑则由项目负责人拍板。
- 对既有页面做改动时，默认遵循"与现状一致"，除非有明确理由升级，且升级动作需同步更新 DESIGN.md。
- 任何对 DESIGN.md 的修改须记录原因与日期（版本控制见 §6）。

## 6. 设计资源管理与版本控制

### 6.1 文件组织
```
design/
├── AGENTS.md        # 本文档：协作规范与原则
├── DESIGN.md        # 视觉与交互标准（token 级规范）
├── CHANGELOG.md     # 设计体系变更记录
└── (后续可扩展：components/、icons/ 等)
```

### 6.2 资源命名规范
- 图标/图片：`小写连字符`，如 `icon-download.svg`、`bg-hero-gradient.png`（渐变资源允许）。
- 设计 token：见 DESIGN.md 的 CSS 变量命名（`--ziyit-*` 前缀）。

### 6.3 版本控制
- 每次修改 DESIGN.md / AGENTS.md 后，在文件顶部版本号 +1，并追加 CHANGELOG 条目。
- 版本格式：`v1.0` → `v1.1`（小改动）→ `v2.0`（体系级重构）。

## 7. 全局硬性约束

- **背景禁止使用图像文件**：所有页面统一使用纯色或 CSS 渐变背景（详见 DESIGN.md §10）。已存在的背景图片（如 `bg.jpg`）在 UI 统一化实施阶段逐一替换。
- **`backrooms/` 目录豁免**：不适用本体系，保持其独立风格。
- 页面必须包含规范化的 `<title>`、`description`、`keywords`、`canonical` 等 SEO 元信息（沿用现有 SEO 优化标准）。

## 8. AI 协作说明

当由 AI 代理生成或修改 UI 时，必须按以下方式工作：
1. 先读取 `design/DESIGN.md` 全文，以其为唯一视觉依据。
2. 生成页面时直接使用其中的 CSS 变量与组件样式，不得发明新 token。
3. 交付前逐项核对 §4.2 评审清单。
4. 若现有代码与 DESIGN.md 冲突，以 DESIGN.md 为准并标注待改造项。
